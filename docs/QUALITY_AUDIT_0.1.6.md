# Reality Splitter 0.1.6 深度质量审计

审计日期：2026-07-25

## 1. 审计目标

本次审计针对用户实际遇到的三类回归：

1. 原有交互文案和信息结构被新版本替换。
2. 已明确移除的微博页面按钮再次出现。
3. 复制的文字无法稳定进入插件，失败时界面还会从抽屉切换成其他形态。

审计范围包括：

- 页面注入与平台分支
- 当前页面抽屉、Side Panel 和历史弹窗路径
- 文案和结果结构
- Content Script 与 Service Worker 消息协议
- 输入状态持久化与失败降级
- 模型输出解析、启发式补全与结果展示
- 构建、版本号、文档和 Git 管理

## 2. 已确认并修复的问题

### P1：微博按钮存在第二条创建路径

普通扫描路径虽然已经关闭，但 `setupWeiboFloatingButton()` 仍会创建独立的浮动按钮，因此旧需求会在后续重构中重新出现。

处理结果：

- 删除微博按钮的创建、定位、显示和移动逻辑。
- 微博只保留选中文字、右键菜单、工具栏和粘贴输入。
- 增加页面级清理守卫，主动移除旧版本遗留的按钮宿主、浮层和浮动按钮。
- 构建校验禁止重新出现微博浮动按钮函数和样式。

### P1：抽屉和 Side Panel 各自维护一套产品文案

两个界面分别硬编码标题、操作名称、空状态和结果分组。只修改其中一个时，产品语言和交互结构就会漂移。

处理结果：

- 新建共享文案合同 `src/shared/productCopy.ts`。
- 抽屉和 Side Panel 共同使用同一套标题、模式、操作、状态和结果区块名称。
- 恢复既有产品名称“现实分层器”和“当前短文文本”等已确认文案。
- 抽屉结果结构重新与 Side Panel 对齐，包括作者观点、作者推断、预测、刺激信号、降速辅助和验证建议。

### P1：抽屉失败后切换界面并丢失输入

Service Worker 在抽屉未响应时打开 Side Panel，旧路径还可能创建独立弹窗，但没有先把本次输入写入共享状态。

处理结果：

- 降级前先保存短文或长文输入及对应工作模式。
- 移除独立弹窗，当前页面抽屉为主界面，Side Panel 仅作为单一降级界面。
- Content Script 回执包含精确版本号，避免新 Service Worker 把消息发送给旧页面脚本。

### P1：版本号存在，但没有真正版本历史

仓库此前没有任何 Git 提交，全部文件都处于未跟踪状态。版本号和 Changelog 无法对应到可恢复的代码快照。

处理结果：

- 将 `0.1.6` 定义为首个质量基线。
- 包版本、Manifest、Content Script、Service Worker 和构建产物使用同一版本。
- 构建脚本检查版本同步、消息协议、文案合同、微博按钮禁用和弹窗路径禁用。
- 本次验证完成后建立 Git 基线提交和本地版本标签。

## 3. 当前架构的主要残余风险

### P1：缺少真实 Chrome 扩展端到端自动化

当前构建检查能够发现静态回归，页面 Harness 能验证抽屉交互，但还不能自动覆盖 Chrome 的 Service Worker、右键菜单、Side Panel、权限和真实站点生命周期。

建议：

- 建立加载 `dist` 的 Playwright Chromium 扩展测试。
- 固定覆盖 X 按钮、微博无按钮、选中文字、右键菜单、粘贴、页面刷新、扩展更新和 Side Panel 降级。
- 保留一份发布前人工冒烟测试表，直到自动化覆盖完成。

### P1：核心文件过大，平台逻辑与界面逻辑耦合

当前主要文件规模：

```text
contentScript.ts          1242 行
aiClient.ts               1289 行
analysisHeuristics.ts      907 行
prompts.ts                 482 行
serviceWorker.ts           482 行
```

`contentScript.ts` 同时负责平台识别、页面注入、选区、抽屉状态、DOM 渲染和消息处理。这正是“删除了一个入口，另一个入口又出现”的结构性原因。

建议拆分：

```text
content/
  controller/
  platforms/x/
  platforms/weibo/
  selection/
  drawer/
  messaging/
```

### P1：模型结果没有完整的运行时 Schema 校验

TypeScript 类型只约束编译期，模型返回值仍主要依赖解析、类型断言和标准化函数。字段类型错误或结构漂移可能进入后续启发式逻辑。

建议：

- 为每种结果建立运行时 Schema。
- 解析失败时保留原始响应、模型、Prompt 版本和失败原因。
- 区分可修复格式错误与语义缺失，不让“JSON 修好”掩盖结果质量问题。

### P1：长文“核查”容易形成能力过度承诺

没有联网来源时，系统只能分析原文内部是否提供证据，不能确认外部世界中的事实。二元的“支持/不支持”也可能把复杂证据压缩成伪确定结论。

建议：

- 明确区分“原文内部支持度”和“外部事实核查”。
- 外部核查必须包含来源、时间、主张与证据对应关系。
- 输出使用“已支持、部分支持、证据不足、相互冲突、无法核查”等状态。

### P1：注意力分诊缺少真实用户目标

当前系统可以生成“跳过、浏览、保存、深挖”建议，但并不知道用户此刻的学习目标、决策任务或关注范围。模型可能把通用价值误当成个人相关性。

建议：

- 在分诊模式中加入可选的当前目标。
- 用户未提供目标时，只判断信息结构，不替用户判断个人相关性。
- 记录用户最终选择，用真实行为评估分诊是否有帮助。

### P2：启发式补全没有展示来源

模型输出、关键词规则和默认兜底会共同形成最终结果，但用户和内部评测无法区分每条内容来自哪里。

建议为关键结果增加：

```text
source: model | heuristic | fallback
confidence: low | medium | high
```

### P2：两个界面仍使用不同渲染技术

共享文案只能防止文字漂移，不能保证 React Side Panel 与原生 DOM 抽屉的布局和条件分支永远一致。

建议先抽取统一的结果 ViewModel 和分组逻辑，再考虑让两种界面共享渲染组件。

### P2：缺少 Prompt 和结果质量回归集

当前检查偏向“能否运行”和“结构是否存在”，不能证明分析结果更忠于原文、更克制或更有帮助。

建议建立 50 至 100 条固定案例，至少评估：

- 忠于原文
- 事实、观点、推断和预测分离
- 不补充原文外事实
- 证据边界
- 降刺激程度
- 替代解释质量
- 下一步是否低成本可执行

## 4. 建议版本路线

### 0.1.7：工程稳定性

- 拆分 Content Script。
- 抽取统一结果 ViewModel。
- 增加平台入口和输入同步单元测试。
- 建立 Chrome 扩展发布前测试矩阵。

### 0.2.0：质量闭环

- 建立第一版 Eval 数据集和评分 Rubric。
- 标记模型、启发式和兜底来源。
- 记录 Prompt、模型、延迟、失败类型和用户反馈。

### 0.3.0：来源与验证

- 建立 Claim、Evidence、Source 和 Timestamp 数据结构。
- 把文本内部分析与联网核查拆成两个清晰模式。
- 先做用户主动触发的有限验证，不直接做开放式 Agent。

## 5. 发布门槛

每次版本发布必须同时满足：

1. `npm run build` 通过。
2. 包版本、Manifest 和运行时代码版本一致。
3. 微博页面没有任何注入按钮。
4. 抽屉和 Side Panel 使用共享文案合同。
5. 页面选区、粘贴和降级输入都不会丢失。
6. 同一版本的固定 Eval 不出现未解释的质量下降。
7. Git 中存在可恢复的提交和版本标签。

这份审计结论不是认为产品需要一次性变复杂，而是建立一条更稳的迭代原则：

> 先保证既有用户合同不被破坏，再增加新能力；先让错误可见和可复现，再讨论模型是否更聪明。
